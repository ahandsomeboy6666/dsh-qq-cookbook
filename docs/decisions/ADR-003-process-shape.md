# ADR-003：桥接作为独立进程

## 状态

待确认。推荐值：**独立 Node 进程，不写成 DSH 进程内插件**。

## 背景

两种形态：独立进程通过 `/api` 与 DSH 通信；或写成 Cordis 插件在 DSH host 内运行，直接调 `ctx.agents`。

后者能力更全（能拿到全部交互事件、少一个进程、无鉴权），但把 QQ 连接的生命周期绑在 DSH 上。

## 决策

桥接作为独立进程运行：

- 入口 `src/main.mjs`，单实例锁（重复启动直接退出并提示）。
- 与 DSH 的唯一耦合点是 `dsh/web-adapter`（见 [ADR-002](ADR-002-dsh-access.md)）。
- 崩溃自动重启由外部守护（`start.bat` / systemd / 计划任务），不内建进程管理器。

## 理由

- **故障隔离**：QQ 协议端断线、WebSocket 重连、消息洪峰都发生在桥接进程内；插件形态下这些会占用 DSH 的宿主进程，最坏情况拖垮 GUI。
- **可独立重启**：改桥接代码、换人格、调白名单不需要重启 DSH（DSH 重启会中断所有正在跑的会话）。
- **可观测**：桥接有自己的日志、状态文件、`/status` 探针；出问题先看它是「QQ 侧断」还是「DSH 侧断」。
- **可测试**：独立进程能用 fixture 回放做离线测试，不需要起 DSH。

代价是多一个进程、多一次 Cookie 鉴权、多一层部署。对单机个人使用，这个代价小于插件形态的耦合风险。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 多一个进程要守护 | 提供 `start.bat`（崩溃自动拉起）与 `npm start`；文档写清「窗口别关」 |
| 鉴权失败导致完全不通 | 探针先验 Cookie 铸造；失败信息指向 `~/.dsh/.credentials.yaml` |
| 单实例锁误伤（上次崩溃残留） | 锁文件带 pid + 启动时间；进程不存在则自动清理 |
| 与 DSH 同机资源竞争 | 单机个人场景可忽略；M3 若跑并发会话再看 |

## 验证

- `node checks/probe-dsh.mjs --json` 的 `bridge.singleInstance` 字段。
- 双开测试：`npm start` 两次，第二次退出码非 0，输出「已有实例」。
- 断线测试：停掉协议端 30 秒再恢复，桥接日志出现「重连成功」且不退出。
