# ADR-007：回复分条与首条早发

## 状态

待确认。推荐值：**三级策略——能拿流式就早发首段，拿不到就整轮+进度占位；长回复一律分条**。

## 背景

QQ 消息不能编辑，所以「流式逐字」在 QQ 上等于刷屏，不可用。但「等整轮结束再发」在 agent 跑工具时会让人干等 20–60 秒，是当前最大的体验断点。

DSH Web `/api` 的事件面里是否暴露 `assistant-stream` 的文本增量，尚未在本机复现（❓，见 [tasks/01-probe-dsh.md](../../tasks/01-probe-dsh.md)）。参考实现 qq-bridge 的做法是「回合结束一次性发」，它把流式列为已知限制。

## 决策

按可用能力分三级，实现同一套「可见时间线」：

1. **有流式（首选）**：收到首个文本增量后，累计 ≥80 字或遇到句末标点即发首条；后续增量按同样规则补发，最多 4 条。
2. **无流式**：整轮结束发；但收到消息后 ≤500ms 先发一条回执（「在弄了」），有工具活动时每 20s 补一条进度。
3. **兜底分条**：任何单条回复 >200 字，按段落 → 句号 → 逗号优先级切成 2–4 条，间隔 600–2800ms 随机。

硬约束：

- 单条 ≤400 字，一次回合最多 4 条，超出合并。
- 分条顺序严格串行；发送失败重试 1 次，仍失败则合并成一条。
- 回执与进度消息在群里默认关闭（避免刷屏），私聊默认开启。
- 与 `tools` 模式互斥：检测到 agent 自己调发送工具时，跳过本轮自动转发，避免双发。

## 理由

- 首条早发直接改善 U1/U2 两个指标（见 [UX 规格](../07-ux-spec.md#三指标可验收)），是体验收益最大的一处。
- 分条模拟真人节奏，且规避 QQ 单条过长时的折叠与限流。
- 三级策略让「流式可用性」这个不确定项不阻塞 M0：先做 2/3 级，探针确认后再开 1 级。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 流式分条导致语义断裂 | 只在句末/段落边界切；单条不足 80 字不发 |
| 分条触发限流 | 间隔 + 冷却 + 每轮上限；群聊更保守 |
| relay 与 tools 双发 | 检测发送类工具调用 → 本轮跳过自动转发 |
| 进度消息变噪音 | 仅私聊、仅工具活动、20s 节流 |
| 乱序 | 单会话串行发送队列，失败重试后才发下一条 |

## 验证

- [tasks/07-ux-streaming.md](../../tasks/07-ux-streaming.md)：`npm run test:ux-latency` → P50 ≤3s、P95 ≤8s。
- `npm run test:ux-split` → 1000 字回复切成 2–4 条，间隔在 600–2800ms 内，顺序正确。
- `npm run test:ux-failure` → 注入超时，5s 内出现「重试」提示。
