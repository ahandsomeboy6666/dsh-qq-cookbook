# 方法论：AI 开发范式能不能复用

> 回答一个问题：**「其他项目的开发模式应该也是类似？」**
>
> 答案：骨架相同，但必须先分档。工程类走红绿，品味类走样本收敛。把品味类硬套红绿，会得到一堆测不到东西的绿色。

## 一、先分档

| 类型 | 判据 | 用什么 |
|---|---|---|
| 工程类 | 能写出「跑什么命令、看什么输出」 | 任务卡 + 红绿灯 |
| 品味类 | 只能靠「一听就知道」 | 3 个候选 + 用户排序 |

判据一句话：**你能不能写出一个命令，它失败就代表没做完？** 能 → 工程类；不能 → 品味类。

本项目的例子：白名单是否生效是工程类（`npm test -- guard`）；「她说话像不像人」是品味类（给 3 个版本让用户挑）。

## 二、可复用的六件套

```
AGENTS.md            给 AI 执行者的常驻规则（事实纪律、红绿、禁止事项）
docs/00-proposal.md  为什么做、做到什么程度、不做什么、成功标准
docs/decisions/      ADR + 台账：每个决策的取舍、风险、状态
docs/04-acceptance.md 每个阶段的验收命令与期望输出
tasks/NN-*.md        任务卡：目标/输入/输出/验收/不做什么
checks/              能真跑的检查脚本（资产检查 + 探针）
```

六件套里**只有两样是新的**：事实纪律（版本+出处+标记）和检查脚本（把文档也变成可验收的）。其余是已有实践的组合。

## 三、为什么它有效

| 常见失败 | 六件套怎么防 |
|---|---|
| 文档写完没人看 | AGENTS.md 是 AI 每次开工必读的入口，不是给人看的装饰 |
| 文档与代码脱节 | `check-assets` 校验链接、路径、任务卡结构；代码任务的验收校验行为 |
| 决策拍脑袋、事后找不到原因 | ADR 记录「被否决的方案 + 理由」，否决也留档 |
| 做完发现方向错 | 提案先写非目标与成功标准，开工前就能否掉 |
| 「应该没问题」 | 验收必须是一条命令；人工检查单独列，不混进机器验收 |
| 一上来就是绿 | 流程强制先跑一次红，证明「现在做不到」 |

## 四、新项目 30 分钟初始化

```powershell
# 1. 复制模板
mkdir docs\tasks\checks
copy docs\templates\AGENTS.skeleton.md AGENTS.md
copy docs\templates\proposal.md docs\00-proposal.md
copy docs\templates\task-card.md tasks\01-first-step.md
copy docs\templates\adr.md docs\decisions\ADR-001-first-choice.md

# 2. 填提案：目标、非目标、成功标准、3 条假设
# 3. 写第一个 ADR：最贵/最难回退的那个决策
# 4. 写第一张任务卡：验收必须是命令
# 5. 写 checks/check-assets.mjs 的必需文件清单，跑出红
```

30 分钟能做的只有这些；剩下的在第一个任务卡里长出来。

## 五、红绿的三个变体

| 场景 | 红怎么写 | 绿怎么算 |
|---|---|---|
| 纯代码 | 单元测试断言新行为 | 测试通过 + 旧测试不坏 |
| 文档/资产 | 检查脚本断言结构（缺文件、缺段、链接断） | 脚本全绿 |
| 外部集成 | 探针断言「连得上、版本对」 | 探针退出码 0 |

第三种最容易被忽略：**外部依赖的版本本身就是验收项**。DSH 升级导致静默失效，就是因为没人把版本写进验收。

## 六、与已有范式的关系

| 范式 | 相同 | 差异 |
|---|---|---|
| TDD | 先写失败测试 | 这里把「文档资产」和「外部版本」也纳入测试 |
| ADR | 记录决策与后果 | 这里要求「验证」段必须可执行 |
| Docs-as-code | 文档进版本库 | 这里文档本身被脚本检查结构 |
| Spec-driven | 先规格后实现 | 这里规格必须带「不做什么」与「怎么验」 |

## 七、什么时候不适用

- **探索性研究**：还不知道要做什么时，先做一天原型，别写六件套。
- **一次性脚本**：跑完就扔，写任务卡是浪费。
- **品味类**：语气、视觉、节奏，用样本排序，不要强行写断言。
- **强合规场景**：需要审计签字、变更审批，这套不够，要接正式流程。

## 八、失败模式清单

| 症状 | 根因 | 修法 |
|---|---|---|
| 任务卡写了但没人跑验收 | 验收不是命令，或命令太长 | 缩短成一条 `npm test -- xxx` |
| ADR 变成日记 | 在 ADR 里写实现过程 | 只留决策、理由、风险、验证；过程进 commit |
| 检查脚本越来越像 lint | 检查了风格而不是结构 | 只查「缺了就不能开工」的东西 |
| 文档之间互相抄 | 一篇事实两个家 | 第二处改成链接 |
| 红绿灯永远绿 | 验收没覆盖新行为 | 每加一个功能，先加一条会红的断言 |

## 九、给下一个 agent 的最小上下文

如果只能给接手者三样东西：

1. [`AGENTS.md`](../AGENTS.md) —— 规则与事实纪律。
2. [`docs/01-tech-selection.md`](01-tech-selection.md) —— 为什么这么选、哪些还没验证。
3. [`tasks/`](../tasks/README.md) —— 下一步做什么、怎么算做完。

其余文档都是按需查阅。
