# 30 元零花钱：只靠物理上限

> 决策（2026-10-27）：**不往人设里写额度条款，也不做代码级额度控制**。
> 损失上限 = 小号余额 30 元。

## 一、为什么这么定

| 方案 | 问题 |
|---|---|
| 人设写约束（单笔 30、只给谁买、拒转账） | 软约束，模型可能不遵守；还会让回复带出「按规矩」这种机器人味 |
| 代码级额度闸门 | 插件没有额度字段，要自己加一层拦截，成本高；
而且现在根本没有支付工具，拦的是空气 |
| **物理上限** | 简单、可信、无需维护：账户里只有 30 元，花完就没了 |

## 二、落地（只有一步是人要做的）

1. 小号只充 **30 元**，不绑主号银行卡
2. 不给她支付密码
3. 余额低于 5 元时插件会提醒（`wallet.lowMoney = 5`）

## 三、软件层剩下什么

- `wallet` 只做**余额感知**：能读到余额、低额提醒、余额是否对外披露
- **没有支付工具**：没有支付 MCP，Playwright 里也没有登录支付账号
- 群聊不开放购物：群聊人设里没有相关动作，也没有工具可用

所以现阶段「额度」不是软件管的，是钱本身管。

## 四、`check-budget` 现在验什么

```powershell
node checks/check-budget.mjs
```

| 项 | 含义 |
|---|---|
| 单笔 ≤30 / 每日 ≤60 / 每月 ≤300 / 受益人 / 禁转账 / 日笔数 | 示例配置里的**设计意图**（模板） |
| 生效配置可读 / `wallet` 段存在 | 插件真实配置可读 |
| 人设里含额度条款 | 提示项：预期「没有」，符合当前策略 |
| 物理上限 | **人工**：脚本验不了，要你自己确认小号余额 |

## 五、风险与触发条件

1. **一旦接支付工具**，额度就不再是物理的——那时必须加代码级拦截（金额、受益人、转账类型），不能继续靠余额兜底
2. **浏览器能打开支付页**：不要在 Playwright 的浏览器里登支付账号，否则物理上限失效
3. **充值管不住**：插件只能读余额，拦不住往小号里加钱

## 六、不做什么

- 不写人设级额度条款
- 不给她支付密码，不绑主号银行卡
- 不自动付款
