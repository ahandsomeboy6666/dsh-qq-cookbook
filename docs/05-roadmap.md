# 路线图

> 里程碑验收的完整命令见 [验收矩阵](04-acceptance.md)。本文只管**顺序、依赖、边界**。

## 一、原则

1. **每个里程碑能独立交付、独立验收**：M0 不依赖 M1，M1 不阻塞 M2。
2. **每个里程碑内部先红后绿**：先写验收脚本跑出红，再写实现。
3. **一次只推进一个里程碑**：跨里程碑并行会让「哪一步坏了」无法定位。
4. **决策先于代码**：[ADR](decisions/README.md) 状态不是「已接受」的，不写对应实现。

## 二、里程碑

| 里程碑 | 目标 | 主要交付 | 验收 | 风险 | 估时 |
|---|---|---|---|---|---|
| **M0** 回环 | QQ 发消息，DSH 回消息 | `src/onebot/`、`src/dsh/web-adapter`、`src/main.mjs`、探针 | [M0 表](04-acceptance.md#三m0最小回环) | DSH 协议对不上（V1） | 3–4 人日 |

| **M3** 增强 | 图片、语音、表情、成本看板 | 媒体归一化、MCP 工具、token 账本 | [M3 表](04-acceptance.md#六m3增强) | 多模态与限流 | 5–8 人日 |

## 三、依赖图

```
M0 回环
 ├──► M1 安全（需要 M0 的入站/出站路径才能测越权）
 │      └──► M2 交互（审批转发依赖 M1 的 owner 判定）
 └──► M2 会话（需要 M0 的会话创建）
        └──► M2 人格（依赖会话注入点）
                └──► M3（媒体与成本建立在稳定会话之上）
```

M1 与 M2 的「会话映射」部分可以并行，但共享 `mapping/` 模块，建议串行。

## 五、建议顺序

1. **01 探针** —— 先确认版本、profile、鉴权、协议端四个事实，再写任何代码。
2. **03 通道** —— 先把 QQ 事件稳定收进来（不需要 DSH）。
3. **02 回环** —— 打通一次完整往返，这是整个项目的「hello world」。
4. **05 安全** —— 在扩大使用范围**之前**把边界立起来。
5. **04 会话** —— 持久化映射，重启不丢。
6. **06 人格** —— 最后做，因为它依赖稳定的会话注入点。

## 六、每个里程碑的「不做」

| 里程碑 | 不做 |
|---|---|
| M0 | 不做白名单（但默认拒绝）、不做人格、不做媒体 |
| M1 | 不做语音/表情、不做多账号 |
| M2 | 不做群内仿真（主动插话）、不做黑话学习 |
| M3 | 不做视频、不做多模态生成 |

## 七、时间与人力假设

- 单人 + AI agent 协作，按「人日」估。
- 不含等待 DSH/协议端修复的时间。
- 不含学习 DSH 协议的时间（已由参考实现压缩）。
- 每个里程碑预留 20% 缓冲用于协议适配。
