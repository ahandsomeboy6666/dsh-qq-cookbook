## 一、自建路线原则（已归档）

1. **每个里程碑能独立交付、独立验收**：M0 不依赖 M1，M1 不阻塞 M2。
2. **每个里程碑内部先红后绿**：先写验收脚本跑出红，再写实现。
3. **一次只推进一个里程碑**：跨里程碑并行会让「哪一步坏了」无法定位。
4. **决策先于代码**：[ADR](decisions/README.md) 状态不是「已接受」的，不写对应实现。
5. **体验不是最后一步**：M3 的指标（延迟、分条、打断、静默）在 M0 就开始打点记录。

## 三、依赖图

```
M0 回环
 ├──► M1 安全（要 M0 的入站/出站路径才能测越权）
 │      └──► M2 交互（审批转发依赖 M1 的 owner 判定）
 ├──► M2 会话（要 M0 的会话创建）
 │      ├──► M2 人格（依赖会话注入点）
 │      └──► M3 分条/打断（依赖会话事件流）
 └──► M3 群聊/路由（依赖 M1 白名单）
        └──► M4 多模态（依赖稳定的出站与限流）
              └──► M4 向导/控制台（最后做，包住全部能力）
```

M1 与 M2 的「会话映射」可以并行，但共享 `mapping/` 模块，建议串行。

## 五、建议顺序

1. **01 探针** —— 先确认版本、profile、鉴权、协议端四个事实，再写任何代码。
2. **03 通道** —— 先把 QQ 事件稳定收进来（不需要 DSH）。
3. **02 回环** —— 打通一次完整往返，这是整个项目的「hello world」。
4. **05 安全** —— 在扩大使用范围**之前**把边界立起来。
5. **04 会话** —— 持久化映射，重启不丢。
6. **06 人格** —— 最后做，因为它依赖稳定的会话注入点。
7. **07 分条** —— 体验第一刀：让首条更早到、长回复更好读。
8. **08 打断** —— 让用户觉得「被听见」。
9. **09 多模态** —— 图片先行，语音/表情随后。

## 六、每个里程碑的「不做」

| 里程碑 | 不做 |
|---|---|
| M0 | 不做白名单（但默认拒绝）、不做人格、不做媒体 |
| M1 | 不做语音/表情、不做多账号 |
| M2 | 不做群内仿真（主动插话）、不做黑话学习 |
| M3 | 不做语音、不做控制台 |
| M4 | 不做视频、不做多模态生成、不做多租户 |

## 七、时间与人力假设

- 单人 + AI agent 协作，按「人日」估。
- 不含等待 DSH/协议端修复的时间。
- 不含学习 DSH 协议的时间（已由参考实现压缩）。
- 每个里程碑预留 20% 缓冲用于协议适配。
- M3/M4 的 UX 指标可能触发返工：缓冲优先给「延迟不达标」和「分条触发限流」两种情况。
